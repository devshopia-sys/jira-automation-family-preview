Local-first Jira automation family drafts

Turn one Jira automation into a controlled family of drafts.

One rule + declared variations → multiple controlled Jira automation drafts.

COPY → EDIT → CHECK → REPEAT
becomes
EXPORT → ANALYZE → SELECT WHAT VARIES → VALIDATE → GENERATE DISABLED DRAFTS → REVIEW DIFF

The narrow job

For a Jira administrator or consultant adapting one automation pattern into several independently configured variants. You explicitly choose supported fields from a local export-shaped JSON file. The flow produces a parameterized base, a small manifest, disabled candidate drafts, validation exceptions, and a readable diff.

What it does not do

  • No Jira connection, import, enablement, or runtime execution.
  • No automatic mapping of projects, users, accounts, custom fields, scopes, connections, or IDs.
  • No claim to support every Jira automation shape.
  • Unsupported or ambiguous cases are refused rather than guessed.

When it may help

If several rules share the same structure but need different declared values, one reviewed base can replace repeated structural copying. Project-specific values still require an explicit decision and review.

It is not useful when one unchanged Jira multi-project/global rule already covers the job, or when each rule differs substantially.

Example

Starting from one supported local export, select the rule name and supported action values that genuinely vary. Declare two variants, review their diffs, and download two disabled drafts for manual review. The source export is not changed.

ONE LOCAL EXPORT → SELECT FIELDS → DECLARE TWO VARIANTS → REVIEW DIFF → TWO DISABLED DRAFTS

Demonstrated boundary

The local prototype demonstrated this flow on synthetic fixture families and one owner-authorised Jira Cloud export processed locally. In the tested subset, it analysed a field-change trigger with issue-edit and log actions. Generated candidates remained disabled, instance-bound metadata was warned about, and invalid mappings were refused.

It has not been connected to Jira, imported into an instance, or runtime-tested. It does not claim compatibility with every Jira automation shape. Unsupported or ambiguous cases are refused rather than guessed.
